# Tasks：任务文档

> 状态：CURRENT。本文规定**什么任务需要建独立文档、怎么写、怎么归档**。
> 上位约束：任务文档记录"做过什么、怎么做的、验证了什么"，**不是当前架构事实**。发生冲突时以代码和 `../architecture.md` 为准（见 `../README.md` 权威优先级）。

## 1. 是否需要建任务文档

**不是每个改动都要建。** 只有满足以下**任意两条**时才建：

1. 涉及两个及以上模块（跨包改动）；
2. 触及核心机制：Tick 阶段、Effect 流转、SECD 语义、记忆写入、事件分发；
3. 改变了公共接口（REST 端点、Spec 中定义的契约、事件类型）；
4. 需要多轮 Agent 协作（预计超过一次会话）；
5. 有较高知识沉淀价值（涉及你 Knowledge Map 里尚未掌握的部分）；
6. 预期实现时间超过半天。

**以下情况不建**：拼写修正、单文件小修复、纯文档纠错、日志措辞调整、依赖版本微调。这些直接改，在 `../changelog.md` 留一行即可。

判断不清时：**先不建**，等发现改动范围变大再补建。

## 2. 命名与位置

```text
tasks/
├── active/      正在进行的任务
└── completed/   已完成的任务（只归档，不删除）
```

- 命名：`T-NNN-短横线小写英文名.md`，如 `T-001-agent-action-flow.md`、`T-002-api-contract-completion.md`
- 编号：全局递增，不复用。`NNN` 从 `001` 开始，三位数。
- 同一时刻 `active/` 建议不超过 3 份。超过说明任务切得太碎或没收尾。
- `active/` 为空时保留目录（用 `.gitkeep` 占位），因为 git 不追踪空目录。

## 3. 流转规则

| 阶段 | 动作 |
|---|---|
| 开始 | 在 `active/` 新建，状态写"进行中"；方案未确认前，"设计方案"章节可以只写草案并标注"待确认" |
| 实施中 | 「实施记录」按时间追加，**只记录已发生的事实**，不预填计划 |
| 完成 | 测试结果回填后，补齐「知识沉淀」「遗留问题」，移入 `completed/` |
| 放弃 | 不移除。在文件头标注"已放弃 + 原因 + 日期"，同样移入 `completed/` |

**禁止**：在实现之前把"计划"写进「实施记录」或「测试结果」；把未验证的结论写成已完成。

## 4. 模板

```markdown
# T-NNN：任务名称

- 状态：进行中 / 已完成 / 已放弃
- 日期：YYYY-MM-DD 开始，YYYY-MM-DD 完成
- 涉及模块：

## 1. 背景
为什么需要这个任务？从哪发现的？

## 2. 目标
这次最终要实现什么（可验收的表述）。

## 3. 非目标
这次明确不做的事。

## 4. 当前实现调查
现状是什么？涉及哪些类/方法/接口？关键代码位置。

## 5. 设计方案
怎么做？数据流和调用关系怎么变？边界与兼容性如何处理？
（本项目的设计方案统一记录在这里，不再单独建 design/ 目录）

## 6. 修改范围
逐个列出新增/修改/删除的文件。

## 7. 验收标准
- [ ] 功能验收
- [ ] 测试验收
- [ ] 代码检查（git diff 无残留）
- [ ] 文档更新

## 8. 实施记录
按时间追加实际做了什么。

## 9. 测试结果
执行了什么命令，结果如何，日期。未执行就写"未执行"。

## 10. 知识沉淀
本任务涉及哪些机制？对应 KNOWLEDGE_MAP 的哪几行？（只建议，不勾选）

## 11. 遗留问题
还剩什么没解决？下一个任务的输入是什么？
```

## 5. 与其他文档的关系

| 关系 | 说明 |
|---|---|
| 与 `../architecture.md` | 任务完成后，架构事实**只**更新到 architecture.md，任务文档不重复描述当前架构 |
| 与 `../spec/` | 契约变化更新到 spec/，任务文档只记录"为什么改、改了哪些文件" |
| 与 `../decisions/` | 任务中出现影响多模块或不可逆的取舍时，另立 ADR；任务文档引用 ADR 编号 |
| 与 `../changelog.md` | 任务完成后在 changelog 追加一行摘要 + 指向任务文档，不复制全文 |
| 与 `../development/KNOWLEDGE_MAP.md` | 「知识沉淀」章节指向具体知识点，作为你更新知识状态的输入 |
| 与已废弃的 `design/` | `design/` 目录已合并进本机制：单次改动的设计方案写在任务文档第 5 节；跨多任务的长期方案在 tasks 中建一条以 `-umbrella` 结尾的任务承载 |
