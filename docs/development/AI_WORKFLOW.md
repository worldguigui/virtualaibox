# AI_WORKFLOW：Agent 开发协作规范

> 状态：CURRENT。本文规定 AI Agent 在本项目中从接收任务到交付的**标准工作流程、权限边界和文档更新义务**。
> 上位约束：本文不得与 `../README.md` 的权威优先级冲突；冲突时以 `../README.md` 为准。
> 适用范围：所有由 Agent 参与的代码修改、文档修改和调查任务。

## 0. 三条不可违反的事实纪律

这三条是本项目所有文档问题的共同根因，优先级高于本文其他条款。

1. **数字必须带出处。** 任何测试数、类数、端点数、行数，必须同时给出采集命令和采集日期。没有出处的数字不写。
   - 合格：`2026-10-24 / .\mvnw.cmd test / 9 类 75 例全部通过`
   - 不合格：`测试全部通过` / `80 个通过`（后者查无出处）
2. **没运行就不能说通过。** 未实际执行测试时，只能写"未执行测试"，不得写"测试通过""应当通过""预期通过"。引用历史结果时必须注明该结果的日期和来源（如 surefire 报告）。
3. **推测与事实必须分开。** 不确定的内容写 `[UNKNOWN]` 并说明待验证方式；计划中的内容标 `PLANNED`。不得用"疑似""可能""应该"充当结论。

## 1. 七个阶段

每个任务都走这七步。简单任务可以合并阶段（如小修复的"方案设计"可以只有三行），但**不允许跳过阶段三和阶段五**。

### 阶段一：需求理解

- 明确：任务目标、**非目标**（本次明确不做的事）、约束条件。
- 识别可能涉及的模块（对照 `../architecture.md` §2 组件职责表）。
- 存在重大歧义、或任务会触及核心架构/公共接口时，**先问，不猜**。

**产出**：一段任务理解复述 + 非目标清单。
**禁止**：理解不清就开始读代码改代码。

### 阶段二：代码调查

- 先读文档再看代码：`../architecture.md`（组件与不变量）→ 对应 `../spec/`（契约）→ `../logic-walkthrough.md`（调用链与类职责）→ `../decisions/`（为什么这样设计）。
- 检查实际代码：调用链、接口、状态、数据结构、已有测试。
- 确认"文档说的"和"代码做的"是否一致。**不一致时以代码为准，并把差异记录下来**，不要把文档当事实。

**产出**：现状说明（当前如何实现、涉及哪些类和方法）。
**禁止**：调查阶段修改任何代码或文档。

### 阶段三：方案设计

必须回答六个问题：

1. 当前实现是什么（基于阶段二的代码事实）。
2. 计划修改哪些文件、哪些类。
3. 数据流和调用关系会发生什么变化。
4. 异常、边界、兼容性如何处理（含"不改会怎样"）。
5. 是否触及核心架构、公共接口、核心不变量（`../architecture.md` §4 的 13 条）、Spec 契约。
6. 是否需要新增 ADR（判断标准见 `../decisions/` 现有四份的粒度为参考：影响多个模块或不可逆的取舍才立 ADR）。

**产出**：方案说明 + 影响范围 + 需用户确认的点。
**禁止**：方案未确认就动手（例外见 §2 的"可自主"清单）。

### 阶段四：实现

- 按已确认的方案改，**不擅自扩大范围**。
- 优先复用现有抽象：Effect 单向流、`WorldEngine` 领域命令入口、`EffectExecutor` 唯一落地路径等既有机制，不新造平行通道。
- 发现原方案有重大缺陷（如与核心不变量冲突）→ **暂停并反馈**，不自行改方案。

**禁止**：
- 擅自改变核心架构（SECD 内核、Effect 隔离、LLM Oracle 定位、Tick 五阶段）。
- 通过删除、跳过、弱化测试来让结果变绿。
- 修改公共接口却不说明影响范围。
- 顺手重构本次范围外的代码。

### 阶段五：验证

必须按顺序完成，缺一项就不算完成：

1. `.\mvnw.cmd test`（Java 21；本机 `JAVA_HOME` 若为 17 会编译失败，需切换 JDK）
2. 前端改动时：`cd frontend && npm run build`
3. 检查 `git diff`：确认每一处改动都是有意为之，没有调试残留、没有误改文件
4. 对照阶段三的验收标准逐条核对

**禁止**：测试失败但宣称完成；只跑部分测试却写"全部通过"；把"编译通过"当"测试通过"。

### 阶段六：文档更新

按下表判断，**只更新真正变化的文档，不机械全量更新**：

| 发生了什么变化 | 更新哪份文档 |
|---|---|
| 模块职责、组件清单、核心不变量变化 | `../architecture.md`（含 §4 不变量表） |
| 子系统行为语义、输入输出、契约变化 | 对应 `../spec/*.md` |
| 主流程、tick 顺序、公共方法职责变化 | `../logic-walkthrough.md` |
| 出现影响多模块或不可逆的设计取舍 | 新增 `../decisions/ADR-000N-*.md`，并在 `architecture.md` §7 索引登记 |
| 完成一个可识别的变更节点 | `../changelog.md`（只追加） |
| 审计问题的状态变化（且已实际核验） | `../consistency-audit.md` |
| 协作流程、权限边界变化 | 本文 |
| 符合任务记录准入条件（见 `../tasks/README.md`） | 新建 `../tasks/active/T-XXX-*.md` |

**禁止**：为了让文档看起来完整而补写没有代码依据的内容；把计划写成已完成。

### 阶段七：任务交付

最终报告必须包含八项，缺项视为交付不完整：

1. 完成了什么（一句话）
2. 修改了哪些文件（逐个列出）
3. 关键实现方案
4. 执行了哪些测试、命令、结果
5. 哪些问题尚未解决
6. 哪些知识点值得用户理解（用于 `KNOWLEDGE_MAP.md` 的建议，但不自行勾选）
7. 哪些文档被更新、为什么
8. 与代码或原有文档不一致的发现

## 2. 权限边界

### 可以自主决定（无需逐次确认）

- 读取任何文件、执行只读命令、检索代码、运行测试和构建。
- 在已确认方案内选择具体实现细节（命名、局部抽取、日志措辞）。
- 修正明显的文档错误：断链、拼写、过期路径、与代码不符的事实描述。
- 新增测试用例以覆盖已确认的改动。

### 必须先提交方案并获得确认

- 改动核心架构：SECD 内核、Effect 边界、Tick 阶段划分、LLM 定位。
- 改动公共接口：REST 端点签名、`spec/` 中已定义的契约、事件类型。
- 改动核心不变量（`architecture.md` §4 的 13 条中任意一条）。
- 改动核心数据模型：`World`/`WorldState`/`MemoryEntry`/`PersonalityProfile` 的字段语义。
- 删除任何文档、ADR 或历史资料。
- 引入新的顶层模块、包或第三方依赖。

### 绝对禁止

- 删除或覆盖历史 ADR、`archive/` 中的归档内容。
- 把推测描述为已验证的事实。
- 未实际运行测试就声称测试通过。
- 擅自把 `KNOWLEDGE_MAP.md` 中用户的知识状态标记为"已理解"——Agent 只能提出建议，勾选权归用户。
- 在 `consistency-audit.md` 中把未复核的 `UNKNOWN` 直接改成 `RESOLVED`。
- 修改业务代码来完成文档类任务。

## 3. 冲突处置

发现文档之间、文档与代码之间存在矛盾时：

1. **不擅自选一个当正确的**，也不要同时修改两处让它们"看起来一致"。
2. 先判断哪一方是事实来源：代码和测试 > `architecture.md` > `spec/` > `decisions/` > 其他。
3. 若判断为文档错误 → 按 §2"可自主"修正，并在交付报告中说明。
4. 若判断为代码偏离设计 → 停下来报告，由用户决定是改代码还是改设计。
